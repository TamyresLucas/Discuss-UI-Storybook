# Discuss Design System

A pnpm/Turborepo monorepo: `packages/tokens` (design tokens), `packages/ui`
(the component library + Storybook stories), `apps/storybook` (the docs/dev
surface), `apps/playground` (a throwaway Vite app for manually smoke-testing
`@discuss-ds/ui`). Full layout and tooling rationale in
[.context/TECH_STACK_DS.md](.context/TECH_STACK_DS.md).

Before touching anything under `packages/ui` or `packages/tokens`, read:

- [.context/PROJECT_CONTEXT.md](.context/PROJECT_CONTEXT.md) — who consumes this system, what it deliberately is not, and how to route a task to the right doc below.
- [.context/DESIGN_TOKENS.md](.context/DESIGN_TOKENS.md) — the token taxonomy and how CSS vars map to Tailwind.
- [.context/COMPONENT_CONTRACTS.md](.context/COMPONENT_CONTRACTS.md) — the required prop API, file shape, ref/slot rules.
- [.context/ACCESSIBILITY_GUIDELINES.md](.context/ACCESSIBILITY_GUIDELINES.md) — WCAG target, required ARIA patterns, testing bar.
- [.context/STORYBOOK_RULES.md](.context/STORYBOOK_RULES.md) — CSF3 conventions, tags, the placeholder-swap workflow.
- [.context/COMPONENT_STATUS.md](.context/COMPONENT_STATUS.md) — the 76-component build queue and each one's current stage.
- [.context/ARCHITECTURE.md](.context/ARCHITECTURE.md) — the package dependency graph and the MCP-readiness plan.
- [.context/DECISIONS.md](.context/DECISIONS.md) — settled tradeoffs; check before re-litigating one.
- [design.md](design.md) — the design language itself (spacing/color/motion rationale), separate from the token *schema* in `DESIGN_TOKENS.md`.

## Non-negotiable constraints

These prevent the specific failure modes design-system work drifts into.
Treat every one of these as a hard stop, not a style preference — if a task
seems to require breaking one, that's a signal to stop and flag it rather than
find a workaround.

**No arbitrary values.** Never write a hardcoded color (`#1a1a1a`, `rgb(...)`),
a bespoke pixel spacing (`margin: 13px`, `className="mt-[13px]"`), or a
one-off shadow/radius/font-size — in a component file, a story, or Tailwind's
arbitrary-value bracket syntax. Every visual value comes from
`@discuss-ds/tokens`, consumed either through a Tailwind utility class (mapped
to a token in `packages/ui/src/styles/globals.css`) or a raw `var(--sys-*)` /
`var(--comp-*)`. If the token you need doesn't exist yet, add it to
`packages/tokens/src/tokens.css` first — don't inline the value "just this
once." See [.context/DESIGN_TOKENS.md](.context/DESIGN_TOKENS.md).

**Primitive-first composition.** Any component with focus management, portal
rendering, or ARIA-pattern keyboard navigation (dialogs, popovers, dropdown/
context menus, tooltips, comboboxes, accordions, tabs, alert dialogs, sheets…)
must wrap the matching primitive from the `radix-ui` package. Never build that
behavior from scratch with a `<div>`, custom `onKeyDown` handlers, and manual
`aria-*` attributes — that's exactly the class of bug this constraint exists
to prevent. See [.context/ACCESSIBILITY_GUIDELINES.md](.context/ACCESSIBILITY_GUIDELINES.md).

**Zero business logic in components.** A component in `packages/ui` accepts
data and callback props and renders UI. It never calls `fetch`/an API client,
reads app state/a store, knows about routing, or imports application feature
code. If a component needs realistic data to demonstrate itself, that data is
inlined as story args — it is never fetched. See
[.context/COMPONENT_CONTRACTS.md](.context/COMPONENT_CONTRACTS.md).

**Component-first documentation.** A component implementation file
(`Button.tsx`) is never created without, in the same change:
its story (`Button.stories.tsx`), its test (`Button.test.tsx`), and an export
barrel (`index.ts`) re-exporting it — plus re-exporting from
`packages/ui/src/index.ts` once it's ready to be public. No implementation
lands "to be documented later." See
[.context/COMPONENT_CONTRACTS.md](.context/COMPONENT_CONTRACTS.md) and
[.context/STORYBOOK_RULES.md](.context/STORYBOOK_RULES.md).

**Changesets, not hand-edited changelogs.** Any PR that changes
`packages/tokens` or `packages/ui` includes a changeset (`pnpm changeset`).
`CHANGELOG.md` in those packages is generated by `changeset version` — never
edit a package's `CHANGELOG.md` by hand. See
[.changeset/README.md](.changeset/README.md).

## Everyday commands

```bash
pnpm storybook          # dev server for apps/storybook (packages/ui/src/**/*.stories.tsx)
pnpm playground         # dev server for apps/playground
pnpm build              # turbo: build every package/app
pnpm lint                # turbo: oxlint every package/app
pnpm changeset          # record a change to tokens/ui for the changelog (run before opening a PR)
pnpm version-packages   # apply pending changesets: bump versions + write CHANGELOGs
```
